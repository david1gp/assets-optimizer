# JSON CLI

## Goal

Run assets-optimizer as a Stricli CLI in addition to its existing library API, with centrally validated inputs and JSON output.

## Decisions

- Keep the existing library exports compatible.
- Add `@stricli/core` as a production dependency.
- Use Valibot schemas at the library boundary so CLI and library calls follow the same validation rules.
- Expose every assetsOptimize option as a typed kebab-case flag, with repeated string-array flags and flattened `--ai-label-*` flags.
- Reserve stdout for a single JSON result; send diagnostics and failures through a structured JSON response.
- Follow the repository's Bun, TypeScript, ESM, and test conventions.

## Approach

- Inspect exact public options, result types, logging behavior, and build/package configuration before choosing the command surface.
- Add central runtime validation with minimal changes to the current public API.
- Add a dedicated Stricli application and executable entrypoint that invokes the existing optimizer.
- Test command parsing, validation, JSON success/failure output, and library compatibility.

## Current context

- The public entrypoint is `assetsOptimize(options?: AssetsOptimizeOptions): Promise<AssetsOptimizeResult>` and must remain compatible.
- Strict root and nested schemas now validate the full options object at that entrypoint; lower-level APIs remain unchanged.
- The Stricli CLI captures incidental console output at the requested log level, emits one JSON envelope, and returns a nonzero status for command, validation, or runtime failures.
- Help emits a successful JSON envelope with help text and a zero status.
- The built package exposes `assets-optimizer` through its bin metadata.
- README usage and subprocess coverage now exercise typed-flag success, invalid number and enum parsing, unknown commands, JSON-only output, failure statuses, and library import compatibility.
